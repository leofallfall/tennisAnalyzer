# Baseline benchmarks — 2026-11-18

Everything in this file was **measured**. All other audit documents cite these numbers. When a document uses a number that is not here, it marks it as an estimate.

## Environment

| Item | Value |
|---|---|
| Machine | Cloud VM, 4 vCPU Intel Xeon @ 2.10 GHz, no GPU |
| OS | Linux 6.18 |
| ffmpeg | 6.1.1 (Ubuntu build, libx264, software decode only) |
| Python | 3.12; MediaPipe 1.2.3; OpenCV 5.1.0 |
| Code | commit `2195fc4`, unmodified `tennis_cv.pipeline.run_video_processing` |
| Pose model | MediaPipe PoseLandmarker *full* (pipeline default). The lite and heavy models were tested only in the isolated pose bench. |

Core limits were applied with `taskset`. A vCPU on Railway is not guaranteed to match one of these cores. Treat cross-platform numbers as ±30 %.

## Test media (the critical caveat)

No real tennis footage was available. These inputs were used:

| File | Description |
|---|---|
| `src_1080p60.mp4` | 60 s, 1920×1080, 60 fps, H.264 at 15 Mbit/s, **112.6 MB**. Made by upscaling and padding OpenCV's public pedestrian sample, so it is real people walking, not tennis. It matches a phone's 1080p60 recording in resolution, frame rate and bitrate. |
| `src_hevc_1080p60_20s.mov` | 20 s, 1080p60, HEVC in a `.mov` container (iPhone-like), **19.4 MB** (≈ 58 MB per footage-minute) |

What follows from that:

- **Decode, encode, I/O and RAM figures carry over to tennis footage.** They depend on resolution, fps and bitrate, not on content.
- **Pose time per frame carries over only roughly.** MediaPipe runs its person detector whenever tracking is lost, so the cost depends on how often a person is visible and tracked. The detection rate on this footage (12–55 %) is far below a tennis clip with one player filling the frame.
- **Nothing here measures pose accuracy on tennis strokes.** That is still unmeasured (see `G_BENCHMARK_PLAN.md`).

## 1. Full pipeline (`run_video_processing`, 3600 frames = 1 footage-minute)

| Run | Wall | CPU python | CPU ffmpeg children | Total CPU | Peak RSS python | Preprocess | Decode + quality + pose + overlay loop | Pose ms/frame | Detection rate |
|---|---|---|---|---|---|---|---|---|---|
| 4 cores, stride 1, overlay on (**current default**) | **263.9 s** | 213.3 s | 185.9 s | **399 cpu-s** | 426 MB | 27.2 s | 235.5 s | 31.4 | 0.553 |
| 4 cores, stride 2, overlay off | **89.2 s** | 77.9 s | 91.9 s | 170 cpu-s | 358 MB | 27.6 s | 60.5 s | 29.1 | 0.548 |
| 1 core (`taskset -c 0`), stride 1, overlay | 328.5 s | 176.9 s | 147.3 s | 324 cpu-s | 412 MB | 72.6 s | 254.9 s | 26.7 | — |
| 2 cores, stride 1, overlay | 274.0 s | 188.2 s | 156.9 s | 345 cpu-s | 413 MB | 42.0 s | 230.8 s | 28.3 | — |

Output sizes per footage-minute in the default run:

| Output | Size |
|---|---|
| `proxy.mp4` | 14.87 MB |
| `pose.json` | 10.54 MB (5.22 MB at stride 2) |
| `overlay.mp4` | 7.61 MB |
| `report.json` | < 0.01 MB |

How to read these runs:

- **The current pipeline runs at ~4.4× realtime on 4 cores** (264 s per footage-minute). A 60-minute session would take about 4.4 hours.
- **Extra cores barely help** (1 core 328 s, 2 cores 274 s, 4 cores 264 s). The Python loop runs one frame at a time: python CPU is 213 s out of 264 s wall. Only ffmpeg uses the extra cores.
- **Overlay rendering plus stride 1 is most of the cost.** Turning the overlay off and using stride 2 cuts wall time by 66 % (264 → 89 s).
- Splitting the 235 s loop by subtraction (*derived, not instrumented*):
  - decode ≈ 3600 × 6.7 ms ≈ 24 s
  - pose ≈ 3600 × 31.4 ms ≈ 113 s
  - overlay drawing, MJPEG write and H.264 transcode ≈ 98 s
  - quality sampling: negligible (one frame every 0.5 s)

## 2. Pose model alone (600 decoded 1080p frames held in memory, 4 cores)

| Variant | Stride | Input scale | ms/frame mean | p50 | p95 | Detection rate |
|---|---|---|---|---|---|---|
| lite | 1 | 1.0 | 30.45 | 30.59 | 41.90 | 0.215 |
| full | 1 | 1.0 | 33.41 | 33.18 | 43.58 | 0.120 |
| heavy | 1 | 1.0 | 77.14 | 75.81 | 99.90 | 0.195 |
| full | 2 | 1.0 | 38.42 | 38.17 | 51.25 | 0.123 |
| full | 4 | 1.0 | 36.18 | 36.42 | 45.88 | 0.140 |
| full | 1 | 0.5 | 34.27 | 33.82 | 45.10 | 0.150 |

- Decode with `cv2` (grab + retrieve) took 6.73 ms/frame at 1080p.
- **Lite and full cost almost the same here.** When no one is tracked, the person detector runs on every frame and dominates the cost. Heavy costs 2.3× more.
- **Skipping frames does not make each frame cheaper.** Stride 2 and stride 4 *raise* the cost per frame (VIDEO mode loses tracking and re-runs the detector), so the total saving is smaller than the stride factor.
- **Downscaling the input before MediaPipe saves nothing.** MediaPipe already resizes to its own model input.
- The 3.8 GB RSS in this bench comes from holding 600 frames in memory. It is not pipeline RAM.

| decode HEVC 1080p60 (20 s clip) | 1 | 8.46 s | 8.3 s | — | ≈ 25 cpu-s per minute |
| proxy, **current** settings (≤1920, CFR, x264 veryfast CRF 18) | 4 | 27.67 s | 91.1 s | 402 MB | 14.87 MB |
| proxy, current settings | 1 | 71.22 s | 70.3 s | 232 MB | — |
| proxy, 720p x264 veryfast CRF 23 | 4 | 18.59 s | 51.2 s | 249 MB | **3.21 MB** |
| proxy, 720p CRF 23 | 1 | 45.83 s | 45.2 s | 152 MB | — |
| scan 10 fps @ 256 px, keyframes only (`-skip_frame nokey`) | 1 | 1.82 s | 1.8 s | 72 MB | not a real 10 fps scan, see below |
| scan 10 fps @ 256 px, full decode | 1 | 20.20 s | 19.9 s | 79 MB | — |

- **For H.264, a 10 fps scan costs as much as decoding every frame** (~20 cpu-s per minute). The decoder must decode reference frames anyway.
- The keyframe-only scan is 11× cheaper, but it only sees one frame per GOP (often 1–4 s on phones). That is too sparse for stroke detection, though usable for scene and player-presence checks.
- **A 720p CRF 23 proxy costs 44 % less CPU and is 4.6× smaller** than the current full-resolution CRF 18 proxy.

## Not measured (see the benchmark plan)

- Real tennis footage of any kind: stroke density, detection rate, landmark accuracy at contact, motion blur.
- 10-minute and 30-minute sources. Footage-minutes scale linearly in this pipeline; no state grows with length except `pose.json` in memory.
- Running on Railway itself, and its vCPU speed relative to this VM.
- Claude API token counts on real evidence packs. The figures in the cost model come from the official token formula, not from API calls.
- RTMPose / ONNX Runtime alternatives and per-window ROI processing.

## Reproduce

Scripts are in `scripts/` next to this file. They are reference copies with hard-coded `/tmp` paths; adjust before use.

- `pipeline_bench.py`: runs the real pipeline.
- `pose_bench.py`: model, stride and scale sweep.
- `runcmd.py`: measures wall, CPU and peak RSS of a child process. Use only with commands that write nothing to stdout.
- `run_all.sh`: the sequence used for this file.

Raw output:

- `2026-11-18-results.jsonl`: pipeline and ffmpeg runs
- `2026-11-18-pose-results.jsonl`: pose sweep
